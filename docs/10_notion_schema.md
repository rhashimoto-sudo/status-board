## 1. 前提 — 2つのシステムの役割分担

status-board は**入力面を持たない**。日々の業務の入力は既存の work-dashboard
（`/Users/r.hashimoto/Desktop/開発/work-dashboard`）が担う。

| | 🗂 work-dashboard | 🎮 status-board |
|---|---|---|
| 扱うもの | 業務タスク・プロジェクト・個人ミッション | 成長の評価・可視化 |

> 二重に持つと必ずズレる。status-board は `page_id` で**参照するだけ**。

## 2. work-dashboard 側の既存構造（読み取り専用で使う）

DB は**単一のタスクDB**。`種別`(select) と `親`(relation・自己参照) でツリーを表現している。

| 概念 | 表現 |
|---|---|
| プロジェクト | `種別 = プロジェクト`、`親` なし |
| フェーズ | `種別 = フェーズ`、`親` = プロジェクト |
| タスク | `種別 = タスク`、`親` = フェーズ or プロジェクト |

### 2.1 status-board が使うプロパティ

| プロパティ | 型 | status-board での用途 |
|---|---|---|
| （page.id） | UUID | **証拠の一意キー**。独自採番は存在しない |
| `名前` | title | クエスト名 |
| `ステータス` | select | **`完了` で EXP 算出の対象になる** |
| `完了日` | date | **JST で自動打刻される**。日次集計の基準日 |
| `領域` | select（SEO / MEO / AI開発 / 店頭改善 / その他） | **副軸の決定材料**（§7.1） |
| `作業種別` | select（10分類） | **主軸の決定材料**（§7.1） |
| `見積工数` | number | ❌ **使わない**。221件すべて未入力（§7.3） |
| `優先度` | select | △ 補助のみ。完了タスクの2/3が未設定（§7.3） |
| `親` | relation | プロジェクト・個人ミッションの判別 |

> **`完了` は select であって checkbox ではない。** チェックボックスを探しに行かないこと。

### 2.2 証拠（Evidence）の形式 — 確定

> **証拠 = work-dashboard のタスクへの `page_id` 参照。**

自由記述でも URL 入力でもない。表示用 URL は page_id から決定的に合成できる:

```
https://www.notion.so/{page_id からハイフンを除去した32桁}
```

**この形式を採った理由**（`01_requirements.md` §6「証拠の運用」への回答）:

- 当初案の「URL / ファイル必須、無ければ EXP 0」は**軸によって不公平**だった。
  TECH・DATA は成果物が残るが、INT・PM・BRIDGE は残りにくく、
  **今年の主戦場（`00_profile.md` §4）ほど構造的に不利**になる
- タスク参照なら、成果物が残らない仕事も**タスクとしては実在する**ので全軸で同条件になる
- タスクの期日・完了状態・完了日が向こうにあるため**自己申告で盛れない**
- **入力が増えない**。既に業務で入れているものを指すだけ

### 2.3 個人ミッション

ダッシュボードから除外する方針が確定している（work-dashboard `docs/TODO.md`。未実装）。

> **work-dashboard では非表示、status-board が拾う。** 役割分担として噛み合っている。
> status-board 側も**同じ PJ タイトル定数方式に合わせる**（プロパティを増やさない）。

> （`03_status_system.md` §1.1）。UI で禁止するだけでなく **Notion の選択肢定義の側でも塞ぐ**。
> データの入口で構造的に不可能にしておかないと、Notion から直接編集された時に破れる。

### 3.1 デイリーは査定を通さない

デイリー5個は `Difficulty` / `Novelty` / `Completion` を**持たない**。EXP は 5〜15 の固定。

**理由**: 毎日5回の GM 査定は運用が持たない。またデイリーは「難しさ」ではなく
**「毎日必ず全部やる」という一点だけ**を測る装置である（`05_quest_design.md` §2.1
「部分達成を認めない」の主旨）。難易度を測る対象は仕事タスク・ボス・測定期間の3つ。

### 3.2 作らない DB とその理由

| DB | 判断 | 理由 |
|---|---|---|
| Snapshots | **作らない** | HP・EXP・Lv は**計算結果**。Notion にも置くと計算元とズレ、どちらが正か決められなくなる |
| DefeatLog | **作らない** | 同上。失敗は Quests の `Status = failed` から導出できる |
| HallOfFame | **作らない** | 同上 |

> **原則**: **Notion は「出来事」だけを持つ。「状態」はリポジトリが持つ。**
> `exp.ts` / `penalty.ts` / `level.ts` が唯一の計算元という契約（`08_gm_learning_loop.md`）を守る。
> 履歴は GitHub Actions が `src/data/history.json` に追記し、git がその変更履歴を持つ。

## 4. 接続方式

**status-board から Notion API を直接叩く。** work-dashboard の `/api/tasks` は経由しない。

**理由**: work-dashboard の API は Basic 認証 middleware の配下にあり、
かつ**単一 id を引く GET エンドポイントが存在しない**（`[id]` は PATCH のみ）。
経由すると両者が結合し、work-dashboard の変更が status-board を壊しうる。
同じ Integration Token で両方の DB を直接読めるため、経由する利点が無い。

> Notion の Integration は **DB ごとに接続を許可する**方式。
> Quests DB と work-dashboard タスクDB の**両方に接続**しておくこと（片方だけだと 404）。

### 4.1 同期フロー

```
Notion（work-dashboard タスクDB + status-board Quests DB）
   │  GitHub Actions / 日次 03:00 JST
   ▼
 ① 完了タスクを取得（完了日ベース）
 ② GM が査定 → exp.ts で EXP 算出
 ③ 未達判定 → penalty.ts で HP 更新
 ④ スナップショットを history.json に追記
 ⑤ src/data/*.json を commit
   ▼
Vercel が push を検知して自動再デプロイ
```

**この方式を採った理由**:

- Step 1 が既に `src/data/*.json` の上に組まれているので**アプリ側の変更が要らない**
- **Vercel に Notion トークンを置かなくて済む**
- Notion が落ちてもダッシュボードは生きたまま
- **git 履歴がそのままスナップショット履歴になる**（無料）

### 4.2 実行時刻を 03:00 JST にする理由

0:00 だと**日をまたいで作業した分が翌日に計上される**。3:00 なら実質的な一日の終わりに合う。
GitHub Actions の cron は UTC なので `0 18 * * *`。

`DISPLAY_TIME_ZONE = "Asia/Tokyo"`（`src/lib/constants.ts`）で確定済み。
work-dashboard の `完了日` も JST で打刻されるため一致する。

> **順序を守ること**: ① 取得 → ② EXP → ③ HP更新 → ④ スナップショット。
> ④ を先にやると更新前の HP が記録される。

## 7. work-dashboard のタスク → 9軸の対応（確定）

実装は `src/lib/constants.ts`（対応表）と `src/lib/work-task.ts`（導出関数）。

### 7.1 原則と対応表

> **`作業種別` =「どの能力を使ったか」→ 主軸**
> **`領域` =「何の分野か」→ 副軸**

領域（SEO / MEO / AI開発）は業務ドメインであって能力ではない。同じ「集計」でも
SEO でも MEO でも使う力は 📊DATA である。**主軸を領域から決めてはならない。**

| 作業種別 | 主軸 | | 領域 | 副軸 |
|---|---|---|---|---|
| 開発実装 / AIリライト運用 | 💻 TECH | | SEO / MEO / 店頭改善 | 📣 MARKETING |
| 集計 / 分析・調査 | 📊 DATA | | AI開発 | 💻 TECH |
| 施策立案・設計 | 🧠 INT | | その他 | なし |
| 施策実装 / 資料・スライド作成 | 📣 MARKETING | | | |
| 報告・定例 / 調整・相談 | 🤝 BRIDGE | | | |
| プロジェクト分解 / **発信・共有** | 👑 PM | | | |

- 主軸と副軸が同じになる場合は**副軸を落とす**（実測最多の「AI開発 × 開発実装」59件が該当）
- 未知の作業種別は `main: null` を返し、**EXP を付けない**（適当な軸に割り当てるとレーダーの形が意味を失う）
- 🌎 ENGLISH はここに現れない。§4.1 の読み替えにより status-board のデイリーから入る（`00_profile.md` §4.1）

> **`発信・共有` は 2026-08-15 時点で Notion 側の選択肢に未反映。** 向こうへの追加が必要。

### 7.2 👑PM はフェーズ完了から供給する

**実測（2026-08-15、完了タスク153件）で PM の獲得は 0 だった。**
「プロジェクト分解」の完了タスクが1件も無いため。今年の主戦場の筆頭（`00_profile.md` §4）
である PM がこのままでは伸びない。

原因は構造的なもので、**PM の仕事は「タスクを実行すること」ではなく
「タスクを設計し、人を動かし、期日に着地させること」**であり、タスク行ではなく
**フェーズの側**に現れるため。よってフェーズ完了を PM のクエストとして扱う。

> **⚠ フェーズ自身の `ステータス` を見てはならない。**
> 実測で **17フェーズすべてが `未着手` のまま**だった。配下タスクは153件完了しているのに、
> フェーズ行の status は運用されていない。これを条件にすると PM は永久に 0 になる。

| 項目 | 決定 |
|---|---|
| 完了判定 | **配下タスクが全件完了**したとき（`isPhaseComplete`） |
| 配下0件 | **完了扱いにしない**（「全部完了」が空虚に真になる。実測で5件該当） |
| 完了日 | 配下タスクの `完了日` の最大値（`phaseCompletedDate`） |
| 難易度 | 配下タスク数から決める。`見積工数` は**221件すべて未入力**で使えない |
| 完遂度 | 期限内 1.0 / 遅延 0.7。期限未設定は減点しない（約束が無かったものを罰しない） |

### 7.3 実測で使えると分かったもの・使えないもの

| フィールド | 充足率 | 判定 |
|---|---|---|
| `領域` / `作業種別` | **221/221** | ✅ 軸判定の土台にできる |
| `完了日` | 147/221（完了タスクには入る） | ✅ 日次集計の基準日 |
| `期限` | 168/221 | ○ 完遂度の判定に使う |
| `優先度` | 108/221（完了タスクの2/3が未設定） | △ 補助にとどめる |
| `見積工数` | **0/221** | ❌ 使わない（§7.4） |

### 7.4 `見積工数` を使わない理由 — 削除もしないこと

> **⚠ この欄を「未入力だから埋めよう」「不要だから消そう」としないこと。両方とも誤り。**

`見積工数` は **work-dashboard の ROI 機能の一部**であり、status-board の難易度とは
**別用途のフィールド**である。0/221 なのは未活用なだけで、設計上の役割は生きている。

```
work-dashboard/src/types/task.ts:104   estimatedHours  // ROI = インパクト ÷ これ
work-dashboard/src/app/api/tasks/[id]/route.ts:113   0以下は 400（ROI が発散するため）
work-dashboard/src/components/tasks/impact-fields.tsx  対象因数 / 想定改善幅 / 見積工数
```

**コード参照が53箇所ある。削除すると work-dashboard の優先順位付けが壊れる。**

| 用途 | 判断 |
|---|---|
| work-dashboard の ROI（優先順位付け） | ✅ **本来の役割。残す** |
| status-board の難易度 D1〜D5 | ❌ **使わない** |

#### status-board が難易度の材料にしない理由

数値の見積欄は「**これはどれくらい大変か**」を機械に伝えるための代理指標である。
機械が文章を読めないので、数字に潰して渡す必要があった。

**しかし GM は LLM である。** タスクには `名前`・`作業種別`・`領域` があり、
221件の履歴もある。**読めば分かるものを、人間が数字に潰して入力する必要はない。**

難易度判定の一貫性は、数値フィールドではなく **rubric** で担保する
（`08_gm_learning_loop.md`）。「MEO の集計は D1」のような条項が蓄積する方が、
未入力になりがちなフィールドより遥かに正確になる。

> **status-board 側の対応は完了している。** Quests DB に `見積工数` を作っておらず、
> 読む実装も存在しない。**work-dashboard のタスクDB は触らない**（§6 のルール）。

#### 参考: 「同種作業の中央値と比較する」案は既に向こうにある

`work-dashboard/src/components/tasks/impact-fields.tsx:14` に
「見積工数は空欄のとき、**作業種別ごとの実績中央値**をプレースホルダで提示する」とある。
status-board 側で同種の仕組みを再実装しないこと。

#### 「作業時間から難易度を出す」案を採らない理由

作業時間（時間計測ログDB）を難易度に直結させる案も検討したが、**採らない**。

1. **時間は難易度ではない。** 単調なデータ入力5時間は D1、詰まりを解く20分は D4
2. **「遅い方が得」になる。** 引き延ばすほど EXP が増える構造が生まれる
3. **習熟を罰する。** 🚀「成長・習熟」は加速燃料（`00_profile.md` §5）だが、
   習熟すれば速くなる。時間が EXP を決めると**上達するほど EXP が減る**

時間データを使うなら、難易度ではなく「**同じ作業種別の所要時間が下がったか**＝習熟の可視化」
に使う方が、燃料マップと整合する。ただし時間計測ログDB は現在 Integration 未接続
（404）で、充足率も未確認。**着手前に必ず充足率を測ること**（`見積工数` と同じ轍を踏まない）。

### 8.1 期限の変更履歴について（保留中の案）

日次スナップショット（§4.1）を git に残す構成なので、**フェーズの `期限` が動いたこと自体を
検出できる**。Notion 単体では取れないが、git 履歴があれば取れる。当初の期限を基準にすれば
「ゴールを動かして帳尻を合わせた」場合も見抜ける見積精度が測れる。**入力は増えない。**

実測（2026-08-15、期限と完了日が揃う112件）:

```
期限内に完了  102件 (91%)
期限からの差  中央値 0日 / 75% 0日 / 90% 0日 / 最大 20日
```
