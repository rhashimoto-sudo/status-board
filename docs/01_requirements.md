## 1. 背景・課題

### 現状の問題

- 自分の成長が**どの方向にどれだけ進んだのかが可視化されていない**。伸びている実感が持てない
- 学習と実行が**混同されている**。「知った」だけで満足し、実際にやり切る量が伴わない
- タスクの**難易度・新規性が評価に反映されない**。楽な作業も難しい挑戦も同じ「1件完了」に潰れる
- **失敗にコストが無い**。やらなくても何も起きないので継続が途切れる
- 弱い領域（英語・他者との橋渡し等）が**得意領域の陰に隠れて放置される**
- 毎日開きたくなる画面が無く、**振り返りの習慣そのものが定着しない**

### 解決したいこと

- 成長を **9つのステータス × Lv × 称号** に落とし込み、**九角形レーダーで形として見える**ようにする
- 🔥LEARNING（知らないことを知る力）と ⚔️EXECUTION（知っていることを実際にやる力）を**分離して対比**し、歪みを突きつける
- EXP を **難易度 × 新規性 × 完遂度 × 構造化ボーナス**で算出し、挑戦と反復を正しく差別化する
- **HP制ペナルティ**を導入し、未達に実際のコストを持たせる。HP 0 で **GAME OVER（全ステータス初期化）**
- **TOTAL Lv を上位5平均×0.6 + 全9平均×0.4** で算出し、弱点を隠せなくする
- **ダーク×ネオンの世界観**で「毎日見たくなる」画面を作る

## 2. ドメインモデル（用語定義）

| 用語 | 定義 |
|---|---|
| **ステータス** | 成長軸。専門7つ + 土台2つ = 計9つ。各 Lv1-100（全軸共通の `levelCap` で段階的に解放）。Lv10刻みの帯ごとに称号を持つ |
| **専門ステータス** | 🧠INT / 💻TECH / 📊DATA / 📣MARKETING / 🌎ENGLISH / 👑PM / 🤝BRIDGE。**クエスト単位で直接付与される** |
| **土台ステータス** | 🔥LEARNING / ⚔️EXECUTION。**手入力せず、専門7つの副産物として自動導出する** |
| **levelCap** | 全軸共通の単一レベル上限。初期値 Lv50。ゲートボス討伐で Lv70 → 90 → 100 と解放される（FR-2-2） |
| **TOTAL Lv** | 9ステータスの**実効Lv**（levelCap適用後）から算出する総合レベル。総合称号を持つ |
| **クエスト** | EXP獲得の単位。デイリー / ゲリラ / ミッション / ボス の4階層 |
| **HP** | 失敗を集約するゲージ。0〜100。0で GAME OVER |
| **デバフ** | 一定期間 EXP 獲得倍率を下げる状態。**重複せず最も重い1つのみ適用** |
| **固有スキル《構造化》** | Rank S の唯一スキル。発動回数で Lv1-10（軸のLv100化とは独立。Skill Lv上限は変更なし）。EXP式の構造化ボーナス倍率を供給する |
| **派生スキル** | 《構造化》から派生する5種。専門ステータスが閾値到達で自動解放。該当ステータス EXP +10% |
| **測定期間（CALIBRATION PHASE）** | 開始から14日間。初期Lvを実測で確定させる。ペナルティ完全免除 |
| **殿堂（Hall of Fame）** | GAME OVER 時に周回の記録を永久保存する場所。`generation` で周回数を数える |
| **generation** | 周回数。GAME OVER のたびに +1 |

### FR-1: 9ステータス体系

| 1 | 🧠 INT | 専門 | 思考力・論理構成・抽象化 |
| 2 | 💻 TECH | 専門 | 実装力・技術理解 |
| 3 | 📊 DATA | 専門 | データ分析・統計・可視化 |
| 4 | 📣 MARKETING | 専門 | 市場理解・訴求設計・需要創造 |
| 5 | 👑 PM | 専門 | 計画・進行管理・リスク統制 |
| 6 | 🤝 BRIDGE | 専門 | 他者との橋渡し・合意形成 |

### FR-2: レベル曲線

**初期100・公比1.6の指数曲線を Lv1-10 の10段で定義し、公比 `1.6^(1/10)` の等比補間で
Lv1-100 の100段に再分割する**（Issue #25 で100段化）。10段ごとに旧10段設計の閾値へ厳密一致させ、
旧設計のカンスト地点 11287 は新 Lv91 にあたる（Lv92〜100 は旧設計に存在しなかった新設領域）。
EXP側のバランス定数（`DIFFICULTY_BASE_EXP` 等）はこの再分割では変更しない。

| Lv | 累積必要EXP |
|---|---|
| 1 | 0 |
| 10 | 88 |
| 20 | 240 |
| 30 | 485 |
| 40 | 876 |
| 50 | 1501 |
| 60 | 2502 |
| 70 | 4103 |
| 80 | 6663 |
| 90 | 10761 |
| 91 | 11287（旧設計のカンスト地点） |
| 100 | 17318 |

- 全100段の閾値は `src/lib/constants.ts` の `LEVEL_THRESHOLDS` が正典（本書は抜粋のみ保持する）
- **境界の定義**: 累積EXP `>=` 閾値でその Lv に到達する（`>=` 判定は変更なし）
- `MAX_LEVEL = 100`。実Lvが100を超えることはない（累積EXPは上限後も加算され続ける）

#### FR-2-1: TOTAL Lv

```
TOTAL Lv = 上位5ステータスの実効Lv平均 × 0.6 + 全9ステータスの実効Lv平均 × 0.4
```

- 「実効Lv」は `min(累積EXPから算出したLv, levelCap)`（FR-2-2）
- 「上位5」は実効Lvの降順で上位5件。同値の場合は軸順（FR-1）で先のものを優先
- 結果は小数第1位まで保持し、**総合称号の判定には `floor()` した整数**を使う
- 尖り（上位5）と穴の無さ（全9）の両方を評価するため、弱点を隠せない

#### FR-2-2: levelCap（全軸共通の単一キャップ）

- **実効Lv = `min(累積EXPから算出したLv, levelCap)`**。全9軸に共通の単一キャップであり、
  ボス1体を討伐すると9軸すべてが同時に解放される
- 初期値は **Lv50**（`INITIAL_LEVEL_CAP`。測定期間の初期Lv上限と一致させる）
- ゲートボス討伐で `LEVEL_CAP_GATES = [50, 70, 90, 100]` の順に解放される

| ゲートボス | 討伐で解放される上限 | 対応する合格条件（`00_profile.md` §3） |
|---|---|---|
| 《実例三件》 | Lv70 | 合格条件1: AIと仕組みで他人の課題を解いた実例3件 |
| 《手順の言語化》 | Lv90 | 合格条件2: 解き方が再現可能な手順として言語化されている |
| 《チーム推進》 | Lv100 | 合格条件3: PMとしてチームを1つ、実際に前に進めた |

> **ルール**: ゲートボスは `00_profile.md` §3「今年の合格条件」3つの転記であり、新規に発明しない。

- **EXP はキャップ中も加算され続ける。** 実効Lv・称号・派生スキル・TOTAL Lv はすべて
  **キャップ後の実効Lv**で判定するが、EXP減点のフロア（FR-6-2）は**キャップを適用しない生Lv**を
  基準にする（キャップ到達中に貯めた EXP が減点で消えてはならないため）
- キャップ到達中は該当軸のEXPバーを「⛔ Lv{cap} 到達。ボス《…》討伐で解放」+ 貯蓄EXP量の表示に切り替える

### FR-3: EXP計算式

```
EXP = 基礎値(難易度)
    × 新規性倍率
    × 完遂度
    × 構造化ボーナス
    × デバフ倍率
```

| 要素 | 値 |
|---|---|
| 基礎値 | D1: **10** / D2: **25** / D3: **60** / D4: **150** / D5: **400** |
| 新規性倍率 | 初挑戦: **1.5** / 2〜5回目: **1.0** / 習熟（6回目以降）: **0.5** |
| 完遂度 | 0.0〜1.0 の実数（GMが判定） |
| 構造化ボーナス | **3ステータス以上に跨るタスクのみ**適用。倍率は《構造化》Lv連動（1.15〜1.50）。跨らない場合は 1.0 |
| デバフ倍率 | 衰弱 ×0.8 / 敗北 ×0.9 / 戦闘不能 ×0.5。**重複せず最も重い1つのみ** |

#### 付与ルール

- **1タスク = 主ステータス1つ + 副ステータス最大1つ**
- **副ステータスは 50% 換算**（主に付与した EXP の 50%）
- **証拠（URL / スクショ / ファイル）が無ければ EXP は 0**
- 🤝BRIDGE は**他者が絡むタスクにのみ**入る（単独作業では付与しない）
- 🔥LEARNING / ⚔️EXECUTION は主・副に選べない（FR-1-1 の導出のみ）

> **Step 1 での扱い**: `src/lib/exp.ts` として実装するが、画面からは呼ばない（Step 3 で GM が使う）。
> 計算式の正しさは単体で検証する。

### FR-5: 固有スキル《構造化》Rank S

**表示場所**: ステータスタブ。**レーダーチャートの中心に紋章**を常時配置し、その直下にスキルツリーパネルを置く。

#### FR-5-1: 成長（累積EXPではなく発動回数）

**発動条件: 3ステータス以上に跨るタスク**。単一分野に閉じた作業では一切上がらない。

| Skill Lv | 累積発動回数 | ボーナス倍率 |
|---|---|---|
| 1 | 0 | ×1.15 |
| 2 | 10 | ×1.20 |
| 3 | 25 | ×1.25 |
| 4 | 50 | ×1.30 |
| 5 | 100 | ×1.35 |
| 6 | 150 | ×1.38 |
| 7 | 220 | ×1.41 |
| 8 | 300 | ×1.44 |
| 9 | 400 | ×1.47 |
| 10 | 500 | ×1.50 |

- **境界の定義**: 発動回数 `>=` 閾値でその Lv（例: 24回 → Lv2 / ×1.20、25回 → Lv3 / ×1.25、99回 → Lv4 / ×1.30、100回 → Lv5 / ×1.35）
- この倍率が EXP式の構造化ボーナスになる（固定値ではない）

#### FR-5-2: 派生ツリー（5種）

対応する専門ステータスが閾値に達すると**自動解放**。常時効果として該当ステータスの EXP **+10%**。

| 派生 | 解放条件（実効Lv） | 常時効果 |
|---|---|---|
| 《データ分析》 | 📊DATA Lv50 | DATA の EXP +10% |
| 《AI開発》 | 💻TECH Lv50 | TECH の EXP +10% |
| 《システム設計》 | 💻TECH Lv70 **かつ** 🧠INT Lv50 | TECH の EXP +10% |
| 《PM》 | 👑PM Lv50 | PM の EXP +10% |
| 《現場との橋渡し》 | 🤝BRIDGE Lv50 | BRIDGE の EXP +10% |

> **ルール**: **全5派生の解放**が最終クラス《AIビジネスアーキテクト》（TOTAL Lv90到達・帯としては
> Lv81〜90帯の称号）の到達条件。
> 未解放の派生も UI に表示し、**解放条件を明示**する（何を伸ばせばよいかが分かるようにする）。

#### FR-6-2: 安全装置（必須）

> **ルール**: 以下の3点は実装の必須要件。破ると体験が壊れる。

1. **日々のEXP減点で Lv・称号は下がらない。** 累積EXPは減るが**現在の生Lv（levelCapを適用しない
   算出Lv）の下限累積EXPでフロア**する（例: 生Lv41（下限926）で 940 EXP のとき −30 されても 926 で
   止まり、Lv41 のまま）。levelCap 到達中に貯めた EXP も同じ基準でフロアされるため、
   キャップの貯蓄が減点で消えることはない
2. **デバフは重複しない。** 複数該当する場合は**最も重い1つのみ**適用（戦闘不能 ×0.5 > 衰弱 ×0.8 > 敗北 ×0.9）
3. **HP は 0..100 でクランプ。** 0未満・100超にならない

#### FR-6-3: ☠ GAME OVER（HP 0）

- 全ステータスの累積EXP・Lv・称号・実績を**初期化**する
- **殿堂（Hall of Fame）に記録を永久保存**する: 最高到達Lv / 獲得した称号 / 討伐したボス / 最長ストリーク / その周回の生存日数
- `generation` を **+1** する
- HP は 100 に戻る

#### FR-6-4: HP収支の設計意図（変更時の目安）

未達 −10 / 全達成 +5 のため、均衡には「全達成:未達 = 2:1」が必要。

| ペース | 週のHP収支 | GAME OVER まで |
|---|---|---|
| 週2日落とす | +5 | 到達しない |
| 週3日落とす | −10 | 約10週 |
| 週4日落とす | −25 | 約4週 |

> **ルール**: 上記すべての数値は `src/lib/constants.ts` に集約し、**1箇所の変更で緩められる**ようにする。
> コンポーネント内にマジックナンバーを直書きしない。

### FR-7: 測定期間（CALIBRATION PHASE）

開始から **14日間**。ここで初期Lvを実測して確定させる。

| 項目 | 内容 |
|---|---|
| 課題 | **9ステータス × 各2クエスト = 18件** をこなす |
| ペナルティ | **完全免除**。HP減少なし・GAME OVER なし・ストリークは記録のみ |
| 測定する値 | 実測時間 / 標準時間の比、完遂率、初挑戦タスクの突破速度、自己申告の経歴 |
| 初期Lv算出 | `clamp(10, 50, round(自己申告点 × 0.4 + 実測点 × 0.6))` — **実測を重く見る**（上限50 = 初期 `levelCap` と同値） |
| 終了時 | 「**覚醒**」演出 → 初期ステータス確定 → 固有スキル解放 → 本編開始 |

#### 描画モード

`phase: "calibration"` のとき、通常モードと描画を切り替える。

| 要素 | 測定期間中の描画 |
|---|---|
| レーダー | 全軸 `???` から始まり、**測定が済んだ軸から順に形になる** |
| HPバー | **`—` 表示**（ペナルティ無償であることを明示） |
| 進行バナー | `CALIBRATION PHASE Day n/14` + `18件中 m件完了` を常時表示 |
| デバフ表示 | 非表示 |

## 4. 非機能要件

### NFR-1: 実行環境・技術スタック

| カテゴリ | 選定 | 理由 |
|---|---|---|
| ランタイム | Node.js **v26.3.0** / npm **11.16.0** | 実機で確認済み |
| フレームワーク | **Next.js 15 App Router** + TypeScript | Vercel との親和性。Step 3 で API Route を足せる |
| スタイル | **Tailwind CSS v4** | 設計トークンを CSS 変数で一元管理できる |
| チャート | **Recharts**（RadarChart / LineChart） | React 宣言的。ダーク配色をカスタムしやすい |
| ヒートマップ | **自前SVG** | ライブラリを足さずに済む単純な格子 |
| データ | `src/data/*.json`（静的ダミー） | Step 1 は外部依存ゼロ |
| 型定義 | `src/lib/types.ts` に集約 | 仕様の単一の正 |
| 定数 | `src/lib/constants.ts` に集約 | **調整値を1箇所で緩められるようにする（必須）** |
| デプロイ | **Vercel Hobby**（GitHub 連携で自動デプロイ） | CLI 不要・無料枠 |

> **ルール**: すべて無料枠で完結させる。有料サービスを前提にしない。

### NFR-2: パフォーマンス

- Step 1 は全データが静的 JSON のため、**サーバー通信なしで初期描画が完了**すること
- カウントダウンは 1秒間隔の更新。**タブ非表示時も破綻しない**（`Date` 差分から毎回再計算し、カウンタを自前で減算しない）

### NFR-3: セキュリティ

- Step 1 は**シークレットを一切持たない**（Notion トークン等は Step 3 で環境変数として導入）
- `src/data/*.json` はダミー値のみ。実在の個人情報を含めない

### NFR-4: アクセシビリティ

- テキストのコントラスト比 **4.5:1 以上**（ダーク背景に対する本文色）
- キーボードナビゲーション対応（**タブ切り替えは Tab / Enter / 矢印キーで操作可能**）
- フォーカスリングを可視化する（`outline-none` での除去禁止）
- タッチターゲットは最小 **44x44px**
- **`prefers-reduced-motion` を尊重する**（発光アニメーション・カウントダウンの点滅を停止する）
- **色だけで情報を伝えない**（HP危険域は色に加えてラベル、デバフは色に加えてアイコン+テキスト）
- 装飾用の絵文字は `aria-hidden` にし、意味を持つ絵文字にはテキストラベルを併記する

### NFR-5: レスポンシブ対応

| ブレークポイント | 幅 | 対応 |
|---|---|---|
| Mobile | **375px** | **必須**（横スクロールが発生しないこと） |
| Tablet | 768px | 必須 |
| Desktop | 1024px | 主要 |
| Wide | 1440px | 任意 |

> **ルール**: **375px で横スクロールを発生させない**。レーダー・折れ線・ヒートマップも含めて画面内に収める。

### NFR-6: ビジュアル要件（ダーク×ネオン / ソロレベリング風）

| 要素 | 方針 |
|---|---|
| 背景 | 純黒ではなく **`#0a0b12` 系の深い藍**。上部にごく淡いグラデーション |
| アクセント | **シアン `#22d3ee` × バイオレット `#8b5cf6` の2色のみ**。多色にしない |
| 罫線 | 細い **1px 半透明**。パネルの角に小さな**ブラケット装飾**を付けて「システムウィンドウ」感を出す |
| 英数字 | **等幅フォント（`ui-monospace`）**。Lv・EXP・HP・カウントダウンは全て等幅で桁を揃える |
| 発光 | `box-shadow` による控えめなグロー。**動く発光はカウントダウンとHP危険域のみ** |
| 状態色 | HP: 緑→黄→赤 ／ 緊急: 赤 ／ デバフ: 紫 |
| モード | **ダーク固定。ライトモードは実装しない**（`color-scheme: dark`） |

> **ルール**: **シアン・バイオレット以外の色を混入させない**。ただし状態色（HP の緑/黄/赤・緊急の赤・デバフの紫）は例外として許可する。
> **チャート実装に着手する前に `dataviz` スキルを読み、配色・軸・凡例・ダークの規約を合わせること。**
