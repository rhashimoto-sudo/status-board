## 決定と根拠

- **levelCap は状態として持たない。** 討伐済みゲートボスの `unlockLevel` 集合（`defeatedGateLevels`）
  だけを JSON に持ち、`computeLevelCap` で毎回導出する。状態として持つと「討伐した事実」と
  「cap の値」が二重管理になり、片方だけ書き換えたときに静かに食い違う。
  `GATE_BOSSES` に無い値は無視する（データが壊れても cap が勝手に上がらない）。
- **ゲートボス3体の `unlockLevel` は 70 / 90 / 100。** 決定5「ゲートは Lv50/70/90（初期キャップ Lv50）」
  の 50 は**初期キャップであってボスの解放先ではない**と読んだ。この読みでないと Lv100 に到達する
  経路が存在しなくなる。**docs の文言と実装の解釈が1対1で対応していない箇所**（下記の乖離リスト）。
- **キャップ到達の判定は cap 非適用の生Lv**（`levelFromExp(exp)`）で行う。cap 済みLvで判定すると
  常に `level === levelCap` 側に潰れて到達を検出できず、貯蓄量が常に 0 になる。
  `exp.test.ts` の不変条件（EXPフロアの基準は生Lv）を UI 側で無効化しないための対。
- **`history.json` は一律×N にしない。** ×10 では末尾が現在値と食い違い（×10 は TOTAL 39・
  実際は 32.6）、軸別も 10刻みの階段になって **Tab3 の右端と Tab1 のヘッダー/レーダーが同じ画面で
  矛盾する**。`status.json` の `expThreeMonthsAgo → exp` を90日で線形補間し、各日の `levels` と
  `totalLevel` を `levelsOf` / `computeTotalLevel` に**実際に通して**算出した。
  左端が Tab1 のゴースト（3ヶ月前）と一致するのも同じ理由による副産物。
